# 已知限制与复现问题

这些问题根据原始源码检查记录。此次工作以整理归档为主，没有静默重写算法或设备控制逻辑。

## 图像处理和路径规划

- 缺少原项目锁定环境。当前电脑默认 Python 的 NumPy 2.4.1 与 scikit-learn 1.3.0 无法一起正常导入；不要直接使用该混合环境运行全流程。`requirements.txt` 给出较保守的 NumPy 1.x 范围，具体测试见验证记录。
- `line_test.py` 依赖红色标定线、裁切比例和 0.6 米标定尺寸。未检出足够直线时，后续下标访问可能失败；垂直线分支中 `p1_`、`p2_` 也存在未赋值情况。
- 水平旋转结果写入 `input/a2.jpg`，后续缩放仍读取 `input/a_0.jpg`，因此最终图不一定包含前一步的旋转效果。
- `path.py` 的 BFS 只保证四邻域等代价网格中的最短路径。后续 RDP 和节点偏移没有做完整的线段碰撞复检，不能把最终折线视为已验证的机器人可行轨迹。
- BFS 无路可达时，`find_path()` 中的 `path` 可能未赋值；`rdp()` 假设输入非空；节点偏移与邻域访问未完整限制图像边界。
- `angle.py` 对重合路径点可能发生除零；图像坐标 y 轴向下，角度方向和小车坐标需要一致标定。
- 部分无人机实验在保存前互换 BGR/RGB，需通过实际红蓝标记确认通道；此次未统一修改。
- 单文件 `coordinate_planner.py` 对 NumPy 数组使用 `if not path_points`，会出现布尔值歧义并导致保存失败；以结题版的 `File.save_points` 为研究参考。
- 单文件 `image_planner.py` 无路时仍正常显示图片并结束，本次配套样例未绘制黄色路径，不能只用退出码判断规划成功。

## 地面机器人与设备执行

- `car_move.py` 在导入时连接机器人和加载模型；`drone.py` 也存在顶层硬件操作。语法检查不得导入它们。
- `car_move.py` 使用 `zip(angles, distance)`，长度不一致会静默截断；没有运行前完整路径审查。
- 起步动作 `x=0.65` 和 `z=90`、速度、图像中心阈值均为固定场地参数。
- 退出判断将整数键码与字符串 `"q"` 比较，原退出键逻辑不生效；摄像头线程缺少显式停止事件。此次未将其当作可直接部署程序。
- 原代码含水弹/执行器调用；本次仅归档，不执行起飞、底盘移动、云台或执行器命令。

## 报告与源码的区别

- 小车结题源码使用 YOLOv8，阈值为 `0.5`；未看到报告部分段落所述的 HOG+BFMatcher 融合识别或完整 PID 控制实现。HOG/BFMatcher 出现在历史拼接模块里。
- 报告中的准确率、跟踪延迟和路径规划耗时没有配套可重复的原始测量日志，本仓库不把它们作为此次验证结果。
- 未找到项目专用的模型训练脚本、训练配置或自训练权重证据，现有代码使用 `yolov8n.pt` 预训练模型。
- 信息交互在归档实现中以图片、角度和距离文件为接口，未发现独立的消息协议或自动调度进程。
